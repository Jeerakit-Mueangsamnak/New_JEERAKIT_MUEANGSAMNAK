A. วัตถุประสงค์ของเอกสาร
======================================================================

เอกสารนี้รวมเนื้อหาจากเอกสารต้นทางทั้งหมดให้เป็นสเปกระบบเดียว โดยจัดระเบียบใหม่เป็น:
1) หลักการสถาปัตยกรรมกลาง
2) Flowchart กระบวนการหลัก
3) Diagram โครงสร้างและความสัมพันธ์
4) Workflow ตามฝ่าย
5) Business Rules
6) Validation / Permission / Audit
7) Stock / Finance Ledger
8) Rental Lifecycle
9) Exception Handling
10) Security / Backup / Reporting / Day Close
11) ภาคผนวกข้อมูลดิบจากต้นฉบับทุกไฟล์แบบครบถ้วน

เป้าหมายคือให้เอกสารนี้ใช้เป็นฐานสำหรับ:
- ออกแบบฐานข้อมูล
- ออกแบบ UI/UX
- ออกแบบ Server/RPC
- เขียน RLS/Permission
- เขียน Test Cases
- ตรวจ Business Rule
- ตรวจความครบถ้วนก่อนพัฒนาจริง

======================================================================
B. หลักการสถาปัตยกรรมกลาง
======================================================================

1. หัวบิลเป็นกลาง
   - บิลเดียวมีทั้ง SALE และ RENTAL ได้
   - SALE/RENTAL อยู่ระดับ Line Item
   - สินค้าเดียวกันอยู่ทั้ง SALE และ RENTAL คนละ Line ได้

2. Transaction เดิมต้องไม่ถูกแก้ทับจนสูญเสียประวัติ
   - Payment ใหม่ = Record ใหม่
   - Return ใหม่ = Record ใหม่
   - Refund ใหม่ = Record ใหม่
   - Renewal = ความสัมพันธ์/ธุรกรรมใหม่
   - Cancel/Void/Correction = Reversal/Compensating Entry

3. สถานะต้องแยกเป็นหลายมิติ
   - Bill Status
   - Payment Status
   - Return Status
   - Rental Status
   - Fulfillment Status
   - Item Condition
   - Appointment Status
   - Notification Status

4. Stock และ Finance ต้องมี Ledger/Movement ของตัวเอง

5. งานที่แก้หลายตารางต้อง Atomic
   - BEGIN
   - Validate
   - Lock
   - Insert/Update
   - Audit
   - COMMIT
   - หากผิด ROLLBACK

6. Notification ไม่ใช่ Source of Truth
   - เป็นตัวชี้ไปยัง Entity จริง

7. Product/Customer ที่มีประวัติห้าม Hard Delete
   - ใช้ active/inactive

8. Permission ต้องตรวจระดับ Action
   - ไม่ควรอิง Role อย่างเดียว

9. Audit สำคัญต้องแก้/ลบไม่ได้โดย User ปกติ

10. Close Bill ต้องตรวจ:
   financial_resolved
   AND merchandise_resolved
   AND exception_resolved

E. บิลขายและเช่าในใบเดียว
======================================================================

หลัก:
- Bill เป็น Header กลาง
- Bill Item แต่ละรายการมี line_mode
- line_mode = SALE | RENTAL
- RENTAL มี Rental Line Detail เพิ่ม
- SALE และ RENTAL ห้าม merge แม้ product_id เดียวกัน

ตัวอย่าง:

BILL B001
|
+-- Line 1 SALE
|   สายไฟ 2 × 500 = 1,000
|
+-- Line 2 RENTAL
|   โต๊ะ 10 × 100/วัน × 3 วัน = 3,000
|
+-- Line 3 RENTAL
|   เก้าอี้ 20 × 20/วัน × 3 วัน = 1,200
|
+-- Line 4 SALE
    ถ่าน AA 4 ชุด

Payment รับรวมที่ Bill ได้
แต่ Revenue/Stock Lifecycle ต้องแยกตาม Line

1. หลักการกลางของระบบ
======================================================================

- ข้อมูลธุรกรรมสำคัญไม่ควรถูกแก้ทับย้อนหลังโดยไม่มีประวัติ
- ทุกการเปลี่ยนแปลงที่มีผลต่อเงิน สต็อก ลูกค้า หรือสถานะบิล ต้อง Audit ได้
- สถานะควรเกิดจากข้อมูลจริง ไม่ใช่ผู้ใช้เปลี่ยนเองโดยไม่มีเงื่อนไข
- งานที่แก้หลายตารางพร้อมกันต้องใช้ Database Transaction
- ถ้าขั้นตอนใดล้มเหลว ต้อง Rollback ทั้งเหตุการณ์
- ข้อมูลสินค้าเก่าไม่ลบจริง ใช้ inactive/archived
- ลูกค้าเช่าต้องมีข้อมูลลูกค้า
- การขายสามารถเป็น Walk-in ได้ตามกฎระบบ
- การชำระหลายครั้งต้องเก็บเป็นหลาย Payment Records
- Refund/Cancel/Correction ใช้ Reversal/Compensating Entry
- สิทธิ์ต้องแยกตามบทบาท
- Notification ต้องเชื่อมกับ Event จริง
- Notification ต้องมีสถานะ unread/read/handled
- ระบบต้องป้องกัน Double Submit และ Duplicate Transaction
- ทุกโมดูลต้องมี created_at, created_by และข้อมูล audit ที่จำเป็น

Appointment
- ห้าม end < start
- ห้ามสร้างเวลาไม่ครบ

- เตือน Conflict

- ตรวจ Permission

1. วัตถุประสงค์
======================================================================

เอกสารนี้รวบรวมแนวคิด กฎธุรกิจ ลำดับการทำงาน เงื่อนไข และโครงสร้างข้อมูล
สำหรับ 2 กระบวนการหลัก ได้แก่

1) การรับคืนสินค้าแบบบางส่วนหลายรอบ
2) การรับชำระเงินแบบบางส่วนหลายรอบ

หลักสำคัญของทั้งสองกระบวนการคือ

- ไม่แก้ทับประวัติธุรกรรมเดิม
- ทุกการรับคืนสร้างเหตุการณ์/รายการใหม่
- ทุกการรับชำระสร้างเหตุการณ์/รายการใหม่
- สถานะปัจจุบันคำนวณจากรายการเหตุการณ์ทั้งหมด
- ต้องสามารถตรวจสอบย้อนหลังได้ว่า ใคร ทำอะไร เมื่อไร จำนวนเท่าไร
- ข้อมูลสต็อกและข้อมูลการเงินต้องไม่เกิดยอดติดลบหรือเกินจริง
- การดำเนินการสำคัญต้องอยู่ใน Transaction เพื่อป้องกันข้อมูลค้างครึ่งทาง
- หากขั้นตอนใดล้มเหลว ต้อง Rollback ทั้งเหตุการณ์นั้น

2. แนวคิดหลักของระบบ
======================================================================

ระบบต้องแยก "เอกสารต้นฉบับ" ออกจาก "เหตุการณ์ที่เกิดหลังจากนั้น"

ตัวอย่าง:

บิลเช่า B001
สินค้าโต๊ะ 10 ตัว
ยอดบิล 10,000 บาท

สิ่งที่ห้ามทำ:
- แก้จำนวนโต๊ะเดิมจาก 10 เป็น 6 เมื่อคืน 4
- แก้ paid_amount เดิมไปเรื่อย ๆ โดยไม่มีประวัติรายการชำระ
- เขียนทับ payment method เดิมเมื่อมีการชำระช่องทางใหม่
- ลบหรือแก้รายการคืนเก่าเพื่อให้ยอดปัจจุบันดูถูกต้อง

สิ่งที่ควรทำ:
- บิลต้นฉบับยังเก็บโต๊ะ 10 ตัวเหมือนเดิม
- รับคืน 4 ตัว = สร้าง Return Event ใหม่
- รับคืนอีก 3 ตัว = สร้าง Return Event ใหม่อีกครั้ง
- จ่าย 3,000 = สร้าง Payment ใหม่
- จ่ายอีก 2,000 = สร้าง Payment ใหม่
- สถานะและยอดคงเหลือคำนวณจาก SUM ของเหตุการณ์ทั้งหมด

======================================================================
3. คำศัพท์และสถานะที่ใช้
======================================================================

3.1 สถานะการชำระเงิน

UNPAID
= ยังไม่มีการชำระเงินที่มีผล

PARTIALLY_PAID
= ชำระแล้วบางส่วน แต่ยอดชำระสะสมยังน้อยกว่ายอดที่ต้องชำระ

PAID
= ยอดชำระที่มีผลเท่ากับยอดที่ต้องชำระ

PARTIALLY_REFUNDED
= มีการคืนเงินบางส่วน

REFUNDED
= คืนเงินครบตามยอดที่กำหนด

3.2 สถานะการคืนสินค้า

NOT_RETURNED
= ยังไม่มีสินค้าถูกคืน

PARTIALLY_RETURNED
= คืนมาแล้วบางส่วน แต่ยังมีสินค้าค้างอยู่กับลูกค้า

RETURNED
= คืนครบตามจำนวนที่ส่งมอบ

3.3 สถานะบิลโดยรวม

DRAFT
= ร่าง

CONFIRMED
= ยืนยันบิลแล้ว

ACTIVE
= กำลังดำเนินการ เช่น มีการส่งมอบแล้ว หรือยังมีภาระค้าง

CLOSED
= สินค้าและการเงินถูกเคลียร์ตามเงื่อนไขแล้ว

CANCELLED
= ยกเลิกด้วยกระบวนการที่ถูกต้องและมีประวัติ

ข้อสำคัญ:
Payment Status, Return Status และ Bill Status ต้องแยกกัน

ตัวอย่าง:
Bill Status    = ACTIVE
Payment Status = PARTIALLY_PAID
Return Status  = PARTIALLY_RETURNED

นี่เป็นสถานะที่ถูกต้องและสามารถเกิดขึ้นพร้อมกันได้

======================================================================
4. สูตรหลัก
======================================================================

4.1 การเงิน

paid_amount
= SUM(payment.amount ของ payment ที่ valid)

balance_due
= bill_total
- paid_amount
- credit_adjustments
+ debit_adjustments

กรณีไม่มี adjustment:

balance_due
= bill_total - paid_amount

เงื่อนไข:

ถ้า paid_amount = 0
=> UNPAID

ถ้า 0 < paid_amount < bill_total
=> PARTIALLY_PAID

ถ้า paid_amount >= bill_total
=> PAID

ระบบต้องมี validation ป้องกัน:
- จำนวนเงิน <= 0
- การรับเงินเกินยอดที่อนุญาตโดยไม่มีกฎรองรับ
- Payment ซ้ำจากการกดปุ่มซ้ำ
- การแก้หรือลบประวัติการชำระโดยไม่มีสิทธิ์
- การรวม split payment หลายช่องทางเป็น record เดียว

4.2 การคืนสินค้า

returned_qty
= SUM(return_line.quantity ของรายการคืนที่ valid)

remaining_qty
= delivered_qty - returned_qty

เงื่อนไข:

ถ้า returned_qty = 0
=> NOT_RETURNED

ถ้า 0 < returned_qty < delivered_qty
=> PARTIALLY_RETURNED

ถ้า returned_qty = delivered_qty
=> RETURNED

ระบบต้องบังคับ:

return_qty > 0

return_qty <= remaining_qty

returned_qty <= delivered_qty

remaining_qty >= 0

ห้ามรับคืนเกินจำนวนที่ส่งออกจริง

11. WORKFLOW: หน้าที่และการส่งต่องาน
======================================================================

ฝ่าย/บทบาทที่ 1: ผู้ขาย / แคชเชียร์

หน้าที่:
- เปิดบิล
- เลือกสินค้า
- เลือกเช่าหรือขาย
- ระบุจำนวนและราคา
- เลือกลูกค้าตามกฎ
- รับชำระเงิน
- เลือกช่องทางการชำระ
- กรอกจำนวนเงินจริง

การส่งต่องาน:
- หลังยืนยันบิล -> ระบบบันทึก Bill + Bill Item
- หลังรับเงิน -> ส่ง Payment ไปยังระบบการเงิน
- ถ้ายังจ่ายไม่ครบ -> บิลยังเปิดค้างได้ตามกฎ
- ถ้าสินค้าพร้อมส่ง -> ส่งต่อไปขั้นตอน Delivery

ฝ่าย/บทบาทที่ 2: ระบบการเงิน

หน้าที่:
- ตรวจยอดบิล
- ตรวจยอดรับเงินสะสม
- ตรวจ duplicate payment
- สร้าง Payment ใหม่ทุกครั้ง
- คำนวณ balance_due
- กำหนด Payment Status
- เก็บ payment method แยกรายการ
- บันทึก Audit

ส่งต่องาน:
- ถ้า balance_due > 0
  -> ส่งสถานะ PARTIALLY_PAID กลับหน้าบิล
- ถ้า balance_due = 0
  -> ส่งสถานะ PAID กลับหน้าบิล

ฝ่าย/บทบาทที่ 3: เจ้าหน้าที่ส่งมอบ / คลัง

หน้าที่:
- ตรวจสินค้า
- ตรวจจำนวนพร้อมใช้งาน
- ส่งมอบตามรายการ
- บันทึก delivered_qty
- บันทึกผู้ส่งมอบและเวลา
- ปรับ stock state จากพร้อมใช้เป็นถูกเช่า/ถูกส่งออก

ส่งต่องาน:
- หลังส่งมอบ -> เปิดภาระ Return ของรายการเช่า
- ระบบคำนวณ remaining_qty เริ่มต้นจาก delivered_qty

ฝ่าย/บทบาทที่ 4: เจ้าหน้าที่รับคืน

หน้าที่:
- เปิดบิล
- ดูรายการที่ยังค้าง
- ตรวจจำนวนที่คืน
- ตรวจสภาพสินค้า
- แยกปกติ/ชำรุด/สูญหาย
- บันทึก Return Transaction
- บันทึก Return Lines

ส่งต่องาน:
- สินค้าปกติ -> ส่งกลับ Stock Available
- สินค้าชำรุด -> ส่งไป Inspection/Repair
- สินค้าสูญหาย -> ส่งไปฝ่ายการเงิน/ตรวจค่าเสียหาย
- หากยังคืนไม่ครบ -> สถานะ PARTIALLY_RETURNED
- หากคืนครบ -> สถานะ RETURNED

ฝ่าย/บทบาทที่ 5: ระบบสต็อก

หน้าที่:
- คุมจำนวนที่ส่งออก
- คุมจำนวนที่คืน
- ป้องกันจำนวนคืนเกิน
- ปรับสถานะของชิ้น/จำนวน
- ไม่ให้สินค้าชำรุดกลับ available โดยอัตโนมัติ
- ป้องกัน oversell/over-rent ด้วย locking ตามจุดที่ต้องใช้

ฝ่าย/บทบาทที่ 6: ผู้มีสิทธิ์อนุมัติ

ใช้กับ:
- Refund
- Cancel
- Write-off
- Lost item
- Damage charge
- แก้รายการผิด
- รายการที่ต้อง reverse

หลัก:
ห้ามลบข้อมูลประวัติ
ให้สร้าง compensating/reversal entry

ฝ่าย/บทบาทที่ 7: Audit

ต้องทราบ:
- ใครทำ
- เมื่อไร
- ทำกับบิลใด
- จำนวนเท่าไร
- ก่อนหน้าเป็นเท่าไร
- หลังรายการเป็นเท่าไร
- เหตุผล
- อุปกรณ์/ช่องทางถ้ามี

12. WORKFLOW รวมตั้งแต่เปิดบิลจนปิด
======================================================================

STEP 1: CREATE BILL
ผู้ใช้สร้างบิล
ระบบสร้าง Bill + Bill Items

STEP 2: CONFIRM
ตรวจราคา จำนวน ลูกค้า เงื่อนไข
ยืนยันบิล

STEP 3: PAYMENT #1
ลูกค้าจ่ายบางส่วน
สร้าง Payment #1
สถานะ = PARTIALLY_PAID

STEP 4: PAYMENT #2 (ถ้ามี)
สร้าง Payment #2
รวมยอดใหม่
ห้ามแก้ Payment #1

STEP 5: DELIVERY
ส่งสินค้า
สร้าง Delivery Record
กำหนด delivered_qty

STEP 6: RETURN #1
คืนบางส่วน
สร้าง Return #1
คำนวณ remaining

STEP 7: RETURN #2
คืนเพิ่ม
สร้าง Return #2
ห้ามแก้ Return #1

STEP 8: DAMAGE / LOST
ถ้ามีชำรุดหรือสูญหาย
แยก stock state
สร้างค่าปรับหรือ adjustment ตามกฎ

STEP 9: PAYMENT เพิ่ม
ถ้ามียอดคงเหลือหรือค่าเสียหาย
สร้าง Payment ใหม่
ห้าม merge

STEP 10: FINAL RETURN
รับคืนส่วนสุดท้าย
returned_qty = delivered_qty

STEP 11: FINAL FINANCIAL CHECK
ตรวจ balance_due

STEP 12: CLOSE
ปิดได้เมื่อเงื่อนไขทั้งหมดครบ

13. เงื่อนไขปิดบิลเช่า
======================================================================

โดยหลักควรตรวจอย่างน้อย:

1. remaining_qty = 0
หรือมี disposition ที่ถูกต้องสำหรับสินค้าสูญหาย/ตัดจำหน่าย

2. balance_due = 0
หรือมีสถานะทางการเงินที่อนุมัติแล้วตามกฎ

3. ไม่มี return transaction ค้างบันทึก

4. ไม่มี stock movement ค้างครึ่งทาง

5. รายการชำรุด/สูญหายถูกส่งต่อและบันทึกแล้ว

6. Audit ครบ

เมื่อครบ:
Bill Status = CLOSED

14. Validation ที่ห้ามตกหล่น
======================================================================

การรับเงิน:
- ห้าม amount = 0
- ห้าม amount < 0
- ห้าม payment ซ้ำจาก double click
- ต้องมี idempotency key หรือวิธีป้องกัน duplicate
- ต้องแยก payment method
- ต้องบันทึกผู้รับเงิน
- ต้องบันทึกเวลา
- ต้องบันทึกสถานะ payment
- ถ้ายกเลิก ห้าม delete ตรง ๆ
- ใช้ reversal/refund/void ตามกฎ

การรับคืน:
- ห้าม return_qty = 0
- ห้าม return_qty < 0
- ห้าม return_qty > remaining_qty
- ห้ามคืนสินค้าที่ไม่เคยส่ง
- ห้ามคืนสินค้าคนละ bill item
- ต้องบันทึก condition
- ต้องบันทึกผู้รับคืน
- ต้องบันทึกเวลา
- สินค้าชำรุดต้องไม่กลับ available
- สินค้าสูญหายต้องไม่เพิ่ม stock

======================================================================
15. Transaction / Locking
======================================================================

ทุกเหตุการณ์สำคัญควรดำเนินการแบบ Atomic

ตัวอย่าง Return:

BEGIN

1. Lock bill item / relevant inventory row
2. อ่าน delivered_qty
3. อ่าน returned_qty
4. คำนวณ remaining_qty
5. Validate return_qty
6. Insert return_transaction
7. Insert return_lines
8. Insert stock movement
9. Insert audit event
10. Update derived/cached status ถ้ามี

COMMIT

หากข้อใดผิด:
ROLLBACK ทั้งหมด

ตัวอย่าง Payment:

16. กรณีพิเศษ
======================================================================

16.1 ลูกค้าคืนของ แต่ยังจ่ายไม่ครบ

ทำได้

ตัวอย่าง:
Payment Status = PARTIALLY_PAID
Return Status = PARTIALLY_RETURNED

ระบบต้องแสดงสองสถานะแยกกัน

16.2 ลูกค้าคืนครบ แต่ยังจ่ายไม่ครบ

Return Status = RETURNED
Payment Status = PARTIALLY_PAID
Bill = ยังไม่ควร CLOSED หากยังมีหนี้

16.3 ลูกค้าจ่ายครบ แต่ยังคืนไม่ครบ

Payment Status = PAID
Return Status = PARTIALLY_RETURNED
Bill = ACTIVE

16.4 คืนบางส่วนและบางชิ้นชำรุด

ตัวอย่าง:
คืน 5
- ปกติ 3
- ชำรุด 2

Return Line อาจแยกเป็น 2 Lines ตาม condition
เพื่อให้ stock movement ถูกต้อง

16.5 สูญหาย

ไม่ถือว่า "คืนเข้าสต็อก"
แต่สามารถถือว่า rental obligation ได้รับการ resolve หลังมีขั้นตอนอนุมัติ/คิดค่าเสียหาย
ต้องแยกจาก returned_qty ที่เป็นของคืนจริง หากต้องการความแม่นยำสูง

16.6 Payment ผิดรายการ

ห้ามแก้ payment เก่าแบบไร้ร่องรอย
ควรใช้ void/reversal แล้วสร้าง payment ใหม่

21. กฎสำคัญเชิงสถาปัตยกรรม
======================================================================

กฎที่ 1:
Original Transaction ต้องรักษาไว้

กฎที่ 2:
Mutation ทางธุรกิจที่มีความหมายต้องสร้าง Event/Transaction ใหม่

กฎที่ 3:
สถานะเป็นผลลัพธ์จากข้อมูล ไม่ใช่ความจริงแหล่งเดียว

กฎที่ 4:
Stock และ Finance ต้องแยก ledger/transaction ของตัวเอง

กฎที่ 5:
Return และ Payment เป็นคนละมิติ

กฎที่ 6:
ทุกเหตุการณ์ต้อง Audit ได้

กฎที่ 7:
Cancel/Refund/Correction ใช้ compensating entry

กฎที่ 8:
งานที่แก้หลายตารางพร้อมกันต้องอยู่ใน database transaction

กฎที่ 9:
ป้องกัน concurrent update ด้วย locking / atomic transaction

กฎที่ 10:
ห้ามให้ stock หรือ balance กลายเป็นค่าที่ไม่สมเหตุผล

3. สูตรหลักที่ใช้ทั้งระบบ
======================================================================

3.1 การเงิน

valid_paid_amount
= SUM(valid payments)

valid_refund_amount
= SUM(valid refunds)

net_paid
= valid_paid_amount - valid_refund_amount

final_amount_due
= actual_rental_charge
+ renewal_charge
+ late_penalty
+ damage_charge
+ lost_charge
+ other_authorized_charges
- discounts
- credits

settlement_balance
= final_amount_due
- net_paid
- deposit_applied

ผลลัพธ์:

ถ้า settlement_balance > 0
=> ลูกค้ายังต้องชำระ

ถ้า settlement_balance = 0
=> การเงินเคลียร์

ถ้า settlement_balance < 0
=> ร้านต้องคืนเงินลูกค้า

3.2 สินค้า

physical_returned_qty
= SUM(ของที่กลับมาจริง)

approved_lost_qty
= SUM(ของที่ยืนยันว่าหายและผ่านอนุมัติ)

resolved_qty
= physical_returned_qty
+ approved_lost_qty
+ approved_disposition_qty

remaining_obligation
= delivered_qty - resolved_qty

ข้อสำคัญ:
ห้ามใช้ lost = returned
เพราะของหายไม่ได้กลับเข้าสต็อกจริง

21. Lost Charge และ Write-off
======================================================================

Lost Charge อาจมาจาก:
- ราคาทดแทน
- ราคาขาย
- ราคาทุน
- ค่าเสื่อม
- เปอร์เซ็นต์ตามอายุ
- Flat Fee
- Contract Replacement Value

ต้องเก็บ:
- charge basis
- amount
- approved_by
- reason
- timestamp

Write-off ใช้เมื่อ:
- ร้านยอมรับภาระขาดทุน
- ไม่สามารถเรียกเก็บลูกค้า
- มีผู้อนุมัติ
- ต้องปิด ledger ให้สมดุล

ห้าม:
Lost -> Write-off อัตโนมัติ

ควร:
Lost -> Charge -> Collection/Deposit -> Approval -> Write-off

- แยก method
- มี reference
- มี actor

- amount > 0
- ต้องเชื่อมเหตุผล
- ต้องมี approval ตามสิทธิ์
- ห้าม refund เกิน refundable balance

Damage
- ต้องมี condition
- ต้องมี inspection
- ห้าม available อัตโนมัติ

Lost
- ต้องมี missing state ก่อน
- ต้องมี approval
- ห้ามเพิ่ม stock
- ห้าม mark returned

- UI สามารถมีปุ่ม [เช่า] [ขาย]
- ปุ่มดังกล่าวเป็น "current mode" สำหรับสินค้าที่จะเพิ่มต่อไป
- เปลี่ยนโหมดกลางบิลได้
- สินค้าเดียวกันสามารถขายและเช่าคนละจำนวนในบิลเดียวกันได้
- Line ที่เป็น SALE และ RENTAL ห้าม merge เข้าด้วยกัน
- หลัง Checkout แต่ละ Line ต้องเดิน Lifecycle ของตัวเอง
- Payment สามารถรับที่ระดับ Bill เดียวได้

7. สูตรคำนวณ
======================================================================

SALE Line:
line_total = sale_price × quantity

RENTAL Line แบบต่อครั้ง:
line_total = rental_price_per_transaction × quantity × period_count

RENTAL Line แบบรายวัน:
line_total = rental_price_per_day × quantity × number_of_days

sale_subtotal = SUM(extended_amount ของ SALE)
rental_subtotal = SUM(extended_amount ของ RENTAL)
subtotal = sale_subtotal + rental_subtotal

grand_total = subtotal - discount + shipping + fees + vat

11. STOCK WORKFLOW
======================================================================

SALE:
AVAILABLE -> RESERVED -> SOLD/DELIVERED
On Hand ลดจริงเมื่อขาย/ส่งมอบตามกฎ

RENTAL:
AVAILABLE -> RESERVED -> RENTED_OUT -> RETURN_PENDING -> RETURNED -> INSPECTION
INSPECTION -> NORMAL -> AVAILABLE
INSPECTION -> DAMAGED -> REPAIR
INSPECTION -> LOST -> LOST/WRITE-OFF

ตัวอย่าง:
มีโต๊ะ 20
ขาย 2
เช่า 10

On Hand หลังขาย = 18
ใน 18:
AVAILABLE = 8
RENTED_OUT = 10

ห้ามสรุปว่า quantity = 8 อย่างเดียว

17. VALIDATION สำคัญ
======================================================================

SALE:
- product.can_sell ต้อง true
- qty > 0
- sale_price >= 0
- Stock เพียงพอ

RENTAL:
- product.can_rent ต้อง true
- qty > 0
- rental_rate >= 0
- period_count > 0
- start_at ต้องมี
- end_at ต้องมี
- end_at > start_at
- ต้องมี Customer

Mixed Bill:
- Validate ทุก Line ก่อน Commit
- ถ้า Line ใดผิด ต้องห้าม Checkout
- ห้าม Commit แค่บาง Line

Stock:
- Lock ตอน Checkout
- ป้องกัน Oversell
- ป้องกัน Over-rent

Payment:
- amount > 0
- ป้องกัน Double Submit
- รองรับหลาย Payment

21. VALIDATION สำคัญ
======================================================================

Document:
- number unique
- ห้าม recycle
- Final แล้วห้ามแก้เลข

Tax/Discount:
- ห้ามส่วนลดเกิน policy
- VAT rate ต้อง valid
- calculation order ต้องแน่นอน

Deposit:
- ห้ามนับเป็น Revenue
- Refund ต้องตรวจ Damage/Lost

Late Fee:
- ต้องใช้ Due Date จริง
- ต้องใช้ Grace Period
- ห้ามคิดซ้ำ

Refund:
- refund <= refundable amount
- ต้องมี reason
- ต้องมี permission/approval

Close Bill:
- merchandise resolved
- finance resolved
- exception resolved

Reservation:
- expiry ต้องมี
- release stock เมื่อหมดอายุ

Backorder:
- ห้ามนับเป็น delivered
- partial delivery ต้องมี record

Stock Count:
- adjustment ต้องมาจาก discrepancy
- ต้อง audit

Credit:
- ตรวจ limit
- ตรวจ overdue

Cash Close:
- expected vs actual
- variance ต้องบันทึก
