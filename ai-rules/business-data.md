# กฎธุรกิจ ข้อมูล และความปลอดภัย

อ่านเมื่อ: งานแตะเงิน สต็อก สิทธิ์ PIN ลูกค้า บิล ฐานข้อมูล RLS/RPC (กฎหลักอยู่ที่ `CLAUDE.md`)

## ลำดับอำนาจของกฎ

1. คำสั่ง/คำตัดสินล่าสุดของเจ้าของในงานนั้น
2. โค้ด migration tests และฐานข้อมูลปัจจุบัน — เป็นหลักฐานของสิ่งที่ระบบทำอยู่
3. README, Skills, คู่มือเครื่องมือ — แนวทางเทคนิคเท่าที่ไม่ขัดข้างบน

- พฤติกรรมปัจจุบันไม่ใช่ข้อพิสูจน์ว่าตรงกับที่เจ้าของต้องการ ต้องเทียบกับคำสั่งเจ้าของเสมอ
- คำสั่งขัดกับข้อจำกัดด้านความปลอดภัยหรือสิทธิ์เข้าถึง → รายงาน ไม่ฝืนทำ
- แหล่งข้างบนขัดกันจนตัดสินแทนไม่ได้ → หยุดถามตาม `CLAUDE.md` ข้อ 8

## ก่อนลงมือ

- ก่อนแตะเงินจริง สต็อก สิทธิ์ หรือข้อมูลส่วนบุคคล → ตรวจ UI → service/server → RPC/RLS → database และ tests เท่าที่จำเป็น
- ระวังข้อมูลลูกค้า บิล การชำระเงิน สต็อก; ก่อนแก้หรือลบข้อมูลที่เสี่ยง ต้องตรวจผลกระทบ และขออนุมัติถ้ามีความเสี่ยงต่อข้อมูลจริง

## จุดตรวจ

- ห้ามเขียนทับ/ลบประวัติธุรกรรมหรือข้อมูลสำคัญเพียงเพื่อให้ยอดหรือหน้าจอดูตรง; ใช้วิธีบันทึกรายการแก้/กลับรายการ (Correction/Reversal)
- งานสำคัญตรวจสิทธิ์และความถูกต้องฝั่ง Server/RPC; ห้ามเพิ่ม PIN ให้ทุกงานเอง
- ตรวจ Transaction (ทำครบทั้งชุดหรือไม่ทำเลย), RLS, Audit, การกดซ้ำไม่ให้เกิดรายการซ้ำ และการย้อนประวัติ เท่าที่เกี่ยวข้อง
- ห้ามให้ Client เขียน Stock/Payment ตรง หรือ `DELETE` ธุรกรรมเพื่อเลี่ยงขั้นตอนฝั่ง Server
- ค่าที่ต้องตั้งค่าได้ ใช้กลไก Settings ไม่ hard-code ตัวเลขจากการเดา
- ห้ามแสดงข้อมูลปลอมเป็นข้อมูลจริงใน UI; fixture/mock ใช้ได้ใน tests หรือสภาพทดสอบที่แยกไว้ ไม่ปะปน production
- Secrets เช่น `SUPABASE_SECRET_KEY` ต้องอยู่ฝั่ง Server เท่านั้น
- การตัดสินใจทางเทคนิคที่ไม่เปลี่ยนพฤติกรรมธุรกิจ เลือกแนวทางมาตรฐานที่สอดคล้องกับโค้ดเดิมได้ ไม่ต้องถามทุกจุด
