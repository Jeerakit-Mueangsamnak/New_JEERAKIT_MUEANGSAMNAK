# ขั้นตอนทำงาน การตรวจ และการจัดการ error

อ่านเมื่อ: งานแก้หลายไฟล์ งานที่ต้องตรวจผล หรือเจอ error ระหว่างทำ (กฎหลักอยู่ที่ `CLAUDE.md`)

## ก่อนแก้ / ระหว่างแก้ / หลังแก้

- **ก่อนแก้:** จับขอบเขตและผลลัพธ์ที่สั่งให้ครบ · อ่านไฟล์และเส้นทางเรียกใช้ที่เกี่ยวข้อง · บั๊กต้องหาหลักฐานและต้นเหตุก่อน ไม่เดาแก้ตามอาการ · ตรวจส่วนที่เจ้าของเคยยืนยันว่าผ่าน หรือที่อนุญาตเป็นพิเศษไว้ ซึ่งต้องรักษาไว้
- **ระหว่างแก้:** แก้เฉพาะจุดที่สั่ง รักษารูปแบบเดิม · ทำงานในขอบเขตเดียวกันให้ครบ แต่ข้อที่ต้องหยุดถาม (`CLAUDE.md` ข้อ 8) มาก่อนการพยายามทำให้จบในรอบเดียว · รักษา dev server เดิม ใช้ Fast Refresh ไม่ restart ถ้าไม่จำเป็น
- **หลังแก้:** ตรวจตามหัวข้อ "ลำดับการตรวจ" ข้างล่าง แล้วรายงานตาม `CLAUDE.md` ข้อ 1

## งานที่แก้หลายไฟล์ (บังคับ)

1. ก่อนแก้ ตรวจ dependency และเส้นทางต้นทางถึงปลายทางเท่าที่จำเป็น (UI → Hook → Service → Server Action/API → RPC/RLS → การแสดงผล และ tests)
2. ปัญหาเดียวกันต้องแก้หลายไฟล์ → แก้ทุกไฟล์ที่ต้องเปลี่ยนให้งานใช้ได้ครบ ห้ามหยุดที่ไฟล์แรกเพียงเพราะไฟล์อื่นไม่ถูกเอ่ยชื่อ
3. ไฟล์ที่เชื่อมกันแต่ไม่ต้องแก้ ให้ตรวจผลกระทบอย่างเดียว ห้าม refactor เพิ่มหรือแก้ส่วนที่ผ่านแล้วโดยไม่มีคำสั่ง
4. แก้ Shared Component, Hook, Service, API, RPC, type หรือ interface → ตรวจจุดเรียกใช้และจุดที่พึ่งพาสัญญาเดิม แก้เฉพาะจุดที่กระทบจริง
5. ต้องแตะไฟล์ใน `CLAUDE.md` ข้อ 5 หรือเปลี่ยนกฎธุรกิจ ฐานข้อมูล migration ข้อมูลจริง → หยุดขอคำสั่งก่อน ห้ามข้ามขั้นเพราะอยากให้งานครบ
6. หลังแก้ รัน test/การตรวจที่ครอบเส้นทางที่เปลี่ยน และตรวจการทำงานร่วมกันจริงเมื่อมีเครื่องมือ; ตรวจบางจุดไม่ได้ = ระบุว่ายังไม่ยืนยัน ห้ามสรุปว่าผ่าน

## ประหยัดเครดิตโดยไม่ลดคุณภาพ

1. ใช้บทสนทนา ผลตรวจล่าสุด และไฟล์ที่อ่านแล้วก่อนเสมอ; อ่านซ้ำเมื่อเนื้อหาเปลี่ยน บริบทไม่ครบ หรือต้องยืนยันผล
2. ค้นจากเส้นทางไฟล์/ชื่อฟังก์ชัน/ข้อความ error ที่รู้ เฉพาะโฟลเดอร์ที่เกี่ยวข้อง; เลี่ยงการ dump ไฟล์ยาว สแกนทั้ง repo และ log ปริมาณมาก
3. ลำดับ: ยืนยันอาการ → ต้นเหตุ → แก้จุดที่เกี่ยวข้อง → ตรวจเฉพาะจุด → ขยายเมื่อมีหลักฐานว่าจำเป็น; ไม่วิเคราะห์หรือแก้เรื่องอื่นแทรก
4. ห้ามรันทดสอบ/ค้นหา/build ซ้ำด้วยเงื่อนไขเดิมโดยไม่มีการเปลี่ยนโค้ด ข้อมูล หรือสมมติฐาน; เก็บผลที่ยังใช้ได้ไว้เป็นหลักฐาน
5. งานเงิน สต็อก สิทธิ์ PIN RLS/RPC หรือ shared component ต้องตรวจเส้นทางและผลกระทบครบ แม้ใช้เครดิตเพิ่ม; ตรวจไม่ได้ให้รายงานว่า **ยังไม่ยืนยัน**
6. งานง่ายใช้โมเดลประหยัด งานซับซ้อนใช้โมเดลที่สามารถพอ (เมื่อเลือกได้); ไม่สร้างไฟล์ทดลองหรือตัวอย่างโดยไม่จำเป็น

## ลำดับการตรวจ

- ตรวจ diff → test เฉพาะไฟล์ที่แก้ → typecheck/lint ตามผลกระทบ → ตรวจหน้าจอ/interaction เมื่อแตะหน้าจอ → ขยายเป็นชุดใหญ่เฉพาะเมื่อมีเหตุผลชัด; ไม่สั่ง full build หรือ `pnpm verify` ทุกครั้งโดยอัตโนมัติ
- `pnpm verify` ใช้เวลานานและสั่ง build; ไม่ใช้แทนการตรวจพฤติกรรมจริง
- แก้เรื่องเงิน สต็อก สิทธิ์ ฐานข้อมูล หรือ shared components → เพิ่มการตรวจ regression ที่จำเป็น แม้ไม่ใช่ชุดที่เร็วที่สุด
- Playwright รันเมื่อยืนยันว่าเป็น Supabase Local แล้ว: `pnpm exec playwright test`

## การจัดการ error

- Error ที่เกิดจากการแก้ครั้งนี้ต้องตรวจและแก้ก่อนส่งงาน อย่าปะปนกับ error เดิมที่ไม่เกี่ยวข้อง
- ไม่ผ่าน → อ่าน error ที่เกี่ยวข้อง แก้สาเหตุ แล้วรันส่วนที่เสียใหม่; ไม่อ้างว่าผ่านจากการไม่มีข้อความ error
- วิธีเดิมไม่สำเร็จ → หาสาเหตุก่อนลองวิธีใหม่ ไม่ลองผิดลองถูกโดยไม่มีหลักฐาน
- รันหรือตรวจไม่ได้เพราะสภาพแวดล้อมหรือขาดสิทธิ์ → รายงาน **ยังไม่ได้รัน / ยังไม่ยืนยัน** พร้อมเหตุผล ไม่เดาผล
